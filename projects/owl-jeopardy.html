Owl Jeopardy

A tool for building and sharing Jeopardy-style review games. Create your own categories and clues, save them as reusable question banks, and share a game so a class can play a live review round. Importing questions straight from a Canvas course and auto-drafting them with Claude are planned for Phase 2.

What it does today (Phase 1)

Build a review game, then share it and play

Owl Jeopardy lets anyone put together a Jeopardy-style review game without wrestling with a slide template. You create the categories and clues, set the point values, and save the result — then share it so a class can play a live review round.

  • Build your own board: add categories and clues, set point values, and edit them any time.
  • Reusable question banks: save a set of questions once and reuse or share it across games.
  • Share & play: hand a game to a class and run a live review round together.
What's next (Phase 2)

Canvas import + AI-drafted boards

The next phase removes the manual entry step: point Owl Jeopardy at a Canvas module and it reads the module's pages, assignments, and readings, then asks Claude to draft a balanced board — categories and clues scaled by difficulty — that an instructor can review and tweak before playing.

Under the hood

How it's built

A React front end drives both the host board and the player buzzers, with a lightweight Python service brokering Canvas content and Claude calls. The AI's job is narrow and well-specified: given cleaned course text, return structured JSON for a validated board — which keeps the output predictable and easy to edit.

Real-time play runs over WebSockets so buzz-ins feel instant, and game state is kept server-side so a dropped phone can rejoin mid-round.

The sprint story

Four weeks, idea to demo

Week 1 — Spec. The team wrote the spec first: what a "board" is, what the Canvas input looks like, and where a human stays in the loop.

Week 2 — Pipeline. Canvas content flowing in, first AI-drafted boards coming out — rough, but real.

Week 3 — Live play. WebSockets, buzzers, and scoring. This is where the timing problems surfaced and got solved.

Week 4 — Polish & demo. Editing UI, caching for the live demo, and a run in front of a real class.
